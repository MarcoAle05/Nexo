# El chat con Claude Code

El cableado con el resto de la app (`sendToClaude`, `printLine`, `LOCAL_COMMANDS`) está en `main.js` (ver `interfaz.md`). El chat con Claude se construyó con `build-design` sobre una imagen de su barra (modelo, esfuerzo, permisos, comandos y Enviar) y se revisó con `better-accessibility` (teclado, nombres, foco y anuncios).

- `claude_code.rs`: el proceso de Claude Code del chat. Lanza `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --forward-subagent-text --permission-prompt-tool stdio` en la raíz del vault, con `--append-system-prompt` (papel de **orquestador**: antes de cada tarea busca una skill o un agente del vault que la cubra y la usa o se la encarga sin que se lo pidan, responde sobre las fuentes buscando en `wiki/fuentes/`, delega la adquisición de fuentes en nexo/Antigravity, sabe guardar conversaciones y escribe en Markdown porque el chat lo pinta), el MCP `playwright` con `--mcp-config` (`navegador/claude-mcp.json`): Chrome **con ventana** sobre el perfil de `browser.rs`, y `--plugin-dir` con un plugin propio de nexo en la carpeta de datos de la app (`install_chat_plugin`, `<datos>/chat-plugin/nexo/`, fuera del vault para que no salga entre las skills del usuario): la skill **`nexo:repertorio`** (`REPERTORIO_SKILL`, con las rutas de verdad puestas al instalarla) le enseña a agregar, quitar, encender y apagar plugins, MCP y skills del repertorio de los workspaces (ver `workspace.md`), y el papel del orquestador le dice que la siga. Lo pidió el usuario el 19-10-2026. Si el plugin no se puede preparar, el chat arranca igual. El módulo es una tubería: `claude_code_send` escribe líneas JSON en la entrada y un hilo reenvía cada línea de la salida por un `Channel` (`{kind: line|exit}`); el protocolo lo interpreta la interfaz (`chat-model.js`). `launch_args` monta y valida los argumentos: modelo, esfuerzo y modo de permisos se pasan solo si el usuario los eligió (si no, manda la configuración de Claude Code) y **nunca** `bypassPermissions` ni `dontAsk` (Claude tiene aquí el navegador con las sesiones del usuario). **Una sesión por apertura de nexo**: la primera vez `--session-id <uuid> --name "Nexo · fecha"`, después `--resume <uuid>` (solo si ya existe su `.jsonl`); al cerrar la app o pedir «conversación nueva» (`claude_code_reset`), la siguiente empieza limpia. Guarda las líneas de la conversación (sin el streaming) para repetírselas a una interfaz recién cargada (`replay`). Antes de lanzar `claude` (aquí y en el sondeo de `registro.rs`) se quitan las variables que Claude Code pone a sus procesos (`INHERITED_ENV`): si nexo se abre desde una terminal de Claude Code las hereda y, con `CLAUDE_CODE_CHILD_SESSION`, Claude Code se toma por sesión hija y **no guarda la transcripción** (ni el historial).
- `chat-model.js`: el protocolo `stream-json` de Claude Code convertido en piezas para pintar, sin DOM (se prueba con node contra una conversación real grabada, `tests/fixtures/chat/turno.jsonl`). `createChatModel().apply(línea)` va montando la lista: mensajes del usuario, texto de Claude (el streaming de `stream_event` escribe la pieza y el mensaje `assistant` completo la cierra), razonamientos, **procesos** (cada `tool_use`, con su estado y su resultado; lo que hace un subagente llega con `parent_tool_use_id` y queda dentro del proceso del agente) y avisos. Un `control_request` `can_use_tool` es un **permiso**: deja el proceso en espera hasta que se contesta con `allowLine`/`denyLine`. De las respuestas de control salen los modelos, los comandos y la suscripción (`initialize`), y el modelo y el esfuerzo vigentes (`get_settings` → `applied`). Los cambios en caliente son peticiones de control: `set_model`, `apply_flag_settings` con `effortLevel` y `set_permission_mode`. Dos líneas son propias (`nexo_user`, `nexo_permission`): las guarda el backend para repetir la conversación, porque lo que escribe el usuario no vuelve por la salida de Claude Code. `nexo_user` puede llevar `to`/`toName` (un mensaje para un agente de un workspace, que se pinta con «Para …») y `local` (no empieza un turno). Con `createChatModel({ prompts: true })` (la ventana de un agente) lo que le dice el orquestador se pinta como suyo («Orquestador»); `touchTool(id)` repinta un proceso cuando cambia algo de fuera (su agente).
- `chat.js`: la vista del chat y su cableado. **Sirve para varios chats**: sus piezas salen de la plantilla `#chat-template` de `index.html` (`mountChat(contenedor, prefijo)` copia la plantilla con los ids bajo un prefijo y reescribe `for`, `aria-controls`… para que apunten dentro de su ventana; la carta derecha usa el prefijo `chat`) y lo que habla con el proceso es un **transporte** (`{ start({ options, replay, onEvent }), send(line, record), reset() }`: el de Nexo va a `claude_code_*`, el del orquestador de un workspace a `workspace_*`). Un chat **alimentado** (`feed`, la ventana de un subagente) no tiene proceso: recibe las líneas que le reparte el workspace (`receive`), lo que escribe el usuario se lo pasa el orquestador (`submitUser`), contesta los permisos por el transporte del orquestador y no enseña los selectores ni los comandos (su campo y sus dos botones van en una fila); «Detener» le pide al orquestador `stop_task` (`onInterrupt`). `relay(cuerpo, registro)` manda a Claude Code un mensaje que se pinta distinto de lo que se manda (lo que el usuario escribe a un agente). Los procesos de Agent llevan debajo «Abrir la ventana de …» cuando el workspace sabe qué agente desplegaron (`agentFor`, `onOpenAgent`). El estado (trabajando, esperando respuesta) sale por `onState`: el punto del riel lo pone `main.js`. Pinta cada pieza una vez y luego solo la que cambia (`model.flush()`); **las piezas lejos del final** (a más de 2400 px o tres alturas de la conversación por encima, `FAR_PX`) llevan `chat-far` y con ella `content-visibility: auto`, así que no se maquetan ni se pintan mientras no se ven (una conversación larga no se vuelve a maquetar entera cuando cambia el ancho de su ventana o de la carta). Cada pieza lleva desde que se pinta `contain-intrinsic-size: auto` para recordar su alto, se marca un fotograma después de pintarse y primero se mide y luego se marca (una lejana deja de maquetarse y movería a las demás): sin eso la conversación dejaba de estar al final. Lo de cerca del final nunca la lleva, para que bajar hasta el final caiga en su sitio, ni la pieza con el foco dentro (`:focus-within`), porque recortaría su anillo. `show()` baja hasta el final enseguida, no en el fotograma siguiente. El Markdown de Claude pasa por `renderMarkdown` (DOMPurify), los procesos son `<details>` nativos y un permiso es una tarjeta con sus botones dentro de la conversación (también las preguntas de Claude, `AskUserQuestion`, y sus planes, `ExitPlanMode`). El compositor lleva adjuntar (los archivos van como rutas en el mensaje), los selectores de **modelo**, **esfuerzo** y **permisos** (botón con menú de la APG: flechas, Inicio/Fin, Escape devuelve el foco), el menú de comandos «/» (lista ligada al campo con `aria-activedescendant`: el foco no sale de él) y **Enviar**, que es «Detener» mientras Claude trabaja con el campo vacío (también Escape). Si la barra no cabe, «Enviar» se queda en su icono (`fitBar`). Lo que cambia sin mover el foco se anuncia en una región `role="status"` (un permiso que llega, el final del turno con la respuesta) y los errores en `role="alert"`; al contestar un permiso el foco vuelve al campo. `/clear` lo atiende nexo (sesión nueva), que es quien lleva la cuenta de la sesión. Lo que empieza por una orden de nexo (`localCommands`) tampoco va a Claude Code ni se pinta como mensaje: así una clave escrita con `/clave` no sale del campo. `userNote` y `reply` dejan en la conversación lo que pasa por la API.
- **Recarga de Vite ≠ reinicio**: al guardar un `.js`, Vite recarga la ventana y se pierde el estado del frontend, pero el backend sigue vivo (el proceso de Claude Code, trabajos de agy). Por eso el lector de la salida de Claude Code sigue leyendo aunque el `Channel` ya no tenga destinatario (si se detuviera, la tubería se llenaría y bloquearía a Claude Code) y guarda la conversación: la interfaz recién cargada llama a `claude_code_start` con `replay`, se vuelve a conectar al proceso en marcha y la recibe entera. Cambiar código en `src-tauri/` sí reinicia la app.
- **La sesión de Claude Code depende de la carpeta**: Claude Code guarda sesiones y memoria por `cwd` (`~/.claude/projects/<cwd codificado>/`). Las sesiones de nexo arrancan en la raíz del vault; si se cambia esa carpeta, `--resume` no encuentra la sesión y la memoria del orquestador queda en otro sitio.
