# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es

**nexo**: un "NotebookLM propio" de escritorio (Tauri 2 + Vite, JS sin framework). Interfaz en español, estilo "Órbita" (negro/blanco, paneles de cristal). Tipografía (`--sans`, `--display`, `--mono` en `styles.css`, cargadas con `@fontsource` en `main.js`): Inter para el texto, Poppins para títulos y cifras grandes, Geist Mono para cifras pequeñas y la terminal; las etiquetas en mayúsculas van en seminegrita con poco espaciado (0.05em). El lienzo del grafo no hereda el CSS: su fuente está en `FONT` de `graph.js`. Tres zonas: fuentes a la izquierda, en el centro (a pantalla completa, detrás de los paneles) la **galaxia** de puntos con las skills alrededor, el **grafo** de la wiki o (en la vista Agentes) el **registro de agentes**, y terminal a la derecha con dos pestañas: **API** (Nexo, Claude por HTTP) y **Claude Code** (terminal real). Vistas de la isla superior: Grafo, Notas y Agentes. Los comentarios, mensajes y textos de UI se escriben en español.

## Comandos

```bash
npm run tauri dev          # app de escritorio con recarga en vivo (arranca Vite en :1420)
npm run dev                # solo la interfaz en el navegador (sin comandos de Tauri)
npm run build              # build del frontend (dist/)
npm run tauri build        # instaladores
npm test                   # pruebas de la interfaz (node --test tests/*.test.mjs)

cd src-tauri
cargo build --no-default-features   # compila el backend sin abrir ventana
cargo test --no-default-features                     # pruebas unitarias
cargo test --no-default-features <nombre>            # una prueba
cargo test --no-default-features -- --ignored        # pruebas de integración (usan markitdown-mcp y ~/.claude reales)
cargo fmt
```

El CI (`.github/workflows/ci.yml`) corre en cada PR y en `main`: `npm test`, `npm run build`, `cargo fmt --check` y `cargo test --no-default-features` (instala antes las dependencias de sistema de Tauri).

Si `cargo` no está en el PATH de la sesión: `source ~/.cargo/env`.

Dependencias externas en tiempo de ejecución: `markitdown-mcp` (instalado con `uv tool install --python 3.12 markitdown-mcp`, en `~/.local/bin`), `playwright-mcp` (`npm install -g --prefix ~/.local @playwright/mcp`; usa el Google Chrome instalado), `claude` (Claude Code CLI) y `agy` (Antigravity CLI). En Linux, `main.rs` llama a `render::configure()` antes de crear nada: elige cómo pinta WebKitGTK (ver `render.rs`); no quitarlo.

## Modelo de datos: el vault

Todo gira en torno a un vault de Obsidian elegido por el usuario (ruta guardada en `~/.config/com.nexo.app/config.json`, junto con la clave de API opcional; el archivo se escribe con permisos 0600):

- `raw/`: fuentes que vuelca el usuario. `raw/markdown/` guarda las conversiones de MarkItDown (misma ruta relativa, extensión `.md`) y **se oculta** del listado de fuentes. `raw/web/*.md` son páginas web leídas por Antigravity y se listan como tipo `web`.
- `wiki/`: notas organizadas por la IA. `_master-index.md` enlaza el `_index.md` de cada carpeta-tema; notas atómicas en kebab-case enlazadas con `[[...]]`.
- `wiki/fuentes/`: **una ficha por fuente** (frontmatter `source: raw/<ruta>`, resumen, ideas clave, `[[conceptos]]`), más `_index.md`. Las mantiene nexo (`fichas.rs`) y el resumen lo escribe Antigravity; `compile` tiene prohibido escribir ahí. Así cualquier fuente se encuentra por su nombre en Markdown.
- `output/`: respuestas (`ask` añade secciones a `output/query-results.md`).
- `wiki/conversaciones/`: conclusiones que Claude Code guarda al pulsar "Guardar en el grafo" (nodos `conversation`).
- `wiki/notas/`: el apartado **Notas**. Temas = carpetas con `_index.md` (`type: tema`, `title`); notas = `.md` con frontmatter `title`, `created`, `updated` (y `date` opcional; el `type` de las notas antiguas ya no se usa). El cuerpo va **una línea por bloque** (texto, `#` títulos, `- [ ]` casillas, viñetas, `1.` listas, `>` citas, `---`, código y tablas) y las fechas se escriben `📅 AAAA-MM-DD`; la fecha de una nota en la lista es la del frontmatter o la 📅 pendiente más próxima. nexo regenera en cada `_index.md` solo la sección entre `<!-- nexo:contenido -->` y `<!-- /nexo:contenido -->` (enlaces a subtemas y notas), así el árbol entero aparece en el grafo.
- `.nexo/escritorio.json`: cartas abiertas en el escritorio de notas (`{cards:[{path,x,y,w,h,z}]}`, rutas relativas a `wiki/notas/`). Lo escribe la interfaz y también Claude Code.
- `.nexo/compiled.json`: manifiesto de fuentes ya compiladas (tamaño:mtime) para no recompilar.
- `.claude/skills/<nombre>/SKILL.md`: las **skills** del usuario, que son skills de Claude Code del vault (la sesión de nexo arranca en la raíz y las carga). nexo lee su frontmatter (`name`, `description` = resumen que ve el usuario, `when_to_use`) y las dibuja alrededor de la galaxia. Las escribe el agente `.claude/agents/creador-de-skills.md` (Sonnet 5.5, `effort: medium`), que nexo instala y mantiene mientras conserve su línea final `<!-- nexo: … -->` (si el usuario la borra, el archivo es suyo).
- `.claude/agents/*.md`: los **agentes** (subagentes de Claude Code) del vault; también los crea `creador-de-skills`, siempre con `model` y `effort` explícitos. nexo los lista en Agentes → Agentes con su `description` como resumen, el modelo y el esfuerzo.

Toda ruta que llega desde la interfaz o desde herramientas del modelo pasa por un guardián que impide salir del vault. `vault::resolve_inside` (fuentes y grafo) y `nexo::wiki_path` (herramientas de compile, cuyas rutas las escribe el modelo) resuelven además los enlaces simbólicos: uno dentro del vault que apunte fuera se rechaza. `notas::resolve` y `agents::agent_file` solo miran el texto de la ruta; sus rutas vienen de la interfaz.

## Arquitectura

**Backend (`src-tauri/src/`)**, todo expuesto como `#[tauri::command]` registrados en `lib.rs`:

- `vault.rs`: configuración, elección del vault, detección de vaults de Obsidian (lee `obsidian.json`) y creación de la estructura.
- `sources.rs`: listar/añadir (copia sin sobrescribir)/abrir/quitar (a la papelera)/renombrar fuentes de `raw/`. Rechaza PDF/Office/EPUB si no está `markitdown-mcp`. `list_sources` sincroniza las fichas (crea las que faltan, manda a la papelera las huérfanas). Renombrar arrastra la conversión, la ficha, el manifiesto y las citas `raw/…` de la wiki.
- `fichas.rs`: fichas de `wiki/fuentes/` (crear, leer para la pestaña de resumen, escribir resumen, renombrar, índice).
- `mcp.rs`: cliente MCP mínimo por stdio (JSON-RPC por líneas) compartido por MarkItDown y Playwright.
- `markitdown.rs`: `markitdown-mcp`, herramienta `convert_to_markdown`. Conversión local, sin IA.
- `playwright.rs`: `playwright-mcp --headless --isolated --browser chrome` (o, si hay navegador cargado y nadie lo tiene abierto, el perfil de `browser.rs` sin ventana): `browser_navigate` → `browser_wait_for` → `browser_evaluate` (extrae el HTML renderizado del contenido principal; el resultado viene en la sección `### Result` del texto) → MarkItDown convierte ese HTML a Markdown. Sin IA.
- `graph.rs`: lee `wiki/` y construye nodos/aristas a partir de `[[enlaces]]` y `[texto](nota.md)`, resolviendo como Obsidian (por ruta o por nombre; con nombres repetidos gana la misma carpeta). El `title:` del frontmatter, si lo hay, es la etiqueta del nodo. Los enlaces rotos son nodos `missing`; las fichas son nodos `source` (con su `source`), las notas de `conversaciones/` son nodos `conversation`, y toda nota que contenga `raw/<ruta>` se une a la ficha de esa fuente.
- `claude.rs`: cliente HTTP de la Messages API (Rust no tiene SDK oficial). Modelo `claude-opus-5-5`, `fallbacks: "default"` con beta `server-side-fallback-2026-07-01`, SSE reconstruido en bloques completos (incluido el pensamiento con su firma). Comprobar siempre `refusal()` antes de usar el contenido.
- `nexo.rs`: el asistente Nexo. `compile` (primero convierte con MarkItDown y envía el Markdown; bucle de herramientas `list_wiki`/`read_note`/`write_note` por fuente), `ask` y chat con la wiki como contexto (presupuesto de caracteres; los índices entran primero). El historial del chat vive en Rust (`ChatState`), es **solo de anexar** y congela el `system` al empezar: no editar ni podar mensajes anteriores (rompe los bloques de pensamiento preservados).
- `vaultgit.rs`: commits automáticos del vault. Si el vault es un repositorio git, `compile` guarda antes de empezar una foto de lo que hubiera sin guardar en `wiki/` (`nexo: antes de compilar`) y, por cada fuente, un commit con las notas que escribió más `.nexo/compiled.json` (`nexo: compila raw/<fuente>`). Llama a `git` como programa: nunca crea el repositorio, nunca empuja y un fallo de git solo deja una línea `git: …` en la terminal, sin tumbar la compilación. Se apaga con `"auto_commit_off": true` en `config.json`. No cubre lo que escriben Claude Code, el editor de notas o Antigravity. Las reglas (C1–C11 e I1–I4) están en `docs/spec-commits-automaticos.md` y cada una tiene su prueba en el módulo.
- `claude_code.rs`: PTY (`portable-pty`) que ejecuta `claude` con `--append-system-prompt` (papel de **orquestador**: antes de cada tarea busca una skill o un agente del vault que la cubra y la usa o se la encarga sin que se lo pidan, responde sobre las fuentes buscando en `wiki/fuentes/`, delega la adquisición de fuentes en nexo/Antigravity y sabe guardar conversaciones). Claude Code ve los agentes y skills nuevos sin reiniciar la sesión. Recibe el MCP `playwright` con `--mcp-config` (`navegador/claude-mcp.json`): Chrome **con ventana** sobre el perfil de `browser.rs`. **Una sesión por apertura de nexo**: la primera vez `--session-id <uuid> --name "Nexo · fecha"` en el vault, después `--resume <uuid>` (solo si ya existe su `.jsonl`); al cerrar la app, la siguiente empieza limpia. Antes de lanzar `claude` (aquí y en el sondeo de `registro.rs`) se quitan las variables que Claude Code pone a sus procesos (`INHERITED_ENV`): si nexo se abre desde una terminal de Claude Code las hereda y, con `CLAUDE_CODE_CHILD_SESSION`, Claude Code se toma por sesión hija y **no guarda la transcripción** (ni el historial).
- `agy.rs`: Antigravity es el **encargado de las fuentes**. `add_web_source(url, playwright)`: sin Playwright, una sola llamada a agy (página → `raw/web/*.md` + resumen de la ficha); con Playwright, la página la lee `playwright.rs` y agy solo resume (sin permiso `read_url`). Ambas fases salen en la misma tarea de Actividad y `summarize_source` (copia el Markdown de la fuente como `fuente.md` en una carpeta vacía de caché y le pide leerlo con `view_file`). Ejecuta `agy "-p=<prompt>" --output-format stream-json --json-schema …`: el prompt va **como argumento** (con `-p=-` no le llega y se pone a explorar carpetas). Los trabajos se serializan (uno a la vez) y cada paso se emite como evento global `agy-activity` para el panel "Actividad Antigravity". Permisos: solo `read_url(<dominio>)` en `~/.gemini/antigravity-cli/settings.json`; nunca `read_url(*)`, `command(...)` ni `--dangerously-skip-permissions` (un permiso denegado aborta la tarea entera).
- `browser.rs`: botón **Cargar navegador** (en Conexiones). Copia el perfil del navegador predeterminado (`xdg-settings`; solo familia Chromium) a `<app_data>/navegador/perfil` sin cachés, extensiones ni sesiones de pestañas, lo abre con Playwright sin ventana para contar las cookies descifradas y solo entonces borra la copia anterior (si Chrome la tenía abierta, lo cierra). `navegador/playwright.json` quita `--password-store=basic`/`--use-mock-keychain` de los argumentos por defecto de Playwright y fija `--password-store=gnome-libsecret` fuera de KDE: sin eso las cookies `v11` (cifradas con el llavero) no se descifran. El perfil original nunca se modifica, y Chrome 136+ no permite automatizar el perfil por defecto, por eso se copia.
- `usage.rs`: límites de uso de las suscripciones, sin gastar cuota. Claude: `GET https://api.anthropic.com/api/oauth/usage` (beta `oauth-2025-04-20`) con el token de `~/.claude/.credentials.json`, solo lectura (si caducó, se pide abrir Claude Code; no se renueva aquí para no invalidar el de Claude Code). Antigravity: no tiene salida para máquinas, así que se abre `agy` en un PTY en una carpeta de caché, se acepta la confianza en la carpeta, se escribe `/usage` y se lee la pantalla «Models & Quota» (porcentaje *restante* por grupo de modelos y «Refreshes in»). ¡Ojo!: `agy -p=/usage` no sirve, en modo `-p` los comandos con barra se mandan al modelo como prompt. Caché de 60 s (Claude; 5 min para el registro de agentes, que estima entre lecturas) y 120 s (agy); «Comprobar de nuevo» fuerza, pero nunca más de una consulta de Claude cada 30 s. El endpoint de Claude responde **429** si se le pregunta a menudo (también lo consulta cada Claude Code abierto) con `Retry-After: 0`: tras un fallo nexo espera 1, 2, 4… hasta 30 min y mientras devuelve la última lectura buena con un aviso (`note`). Esa lectura se guarda en `<caché>/uso-claude.json`. En la interfaz es la mini pestaña junto a Claude Code y Antigravity en Conexiones.
- `notas.rs`: apartado Notas (árbol, leer/crear/guardar notas, crear/renombrar temas, borrar a la papelera, escritorio). `sync` crea `wiki/notas/`, regenera los índices que no estén al día y enlaza `[[notas/_index|Notas]]` desde el índice maestro; solo escribe si algo cambió. `desk_save` recuerda la fecha de su propia escritura para que el vigilante no la confunda con un cambio de Claude Code.
- `render.rs`: cómo pinta WebKitGTK en Linux. Por GPU con `WEBKIT_DMABUF_RENDERER_FORCE_SHM` (el renderizador DMA-BUF da «Error 71» con NVIDIA en Wayland; antes se desactivaba y todo se pintaba por CPU). El ejecutable **exporta su propio `drmWaitVBlank`** (`build.rs` añade `--export-dynamic-symbol`): NVIDIA rechaza esa llamada (`EOPNOTSUPP`) y WebKit caía a un temporizador fijo de 60 Hz; la de nexo prueba la real y, si falla, espera al siguiente refresco calculado con el modo del monitor (120/144 Hz). También desactiva la preferencia `PreferPageRenderingUpdatesNear60FPS`. Al cerrar la ventana mata con SIGKILL los procesos `WebKit*` hijos (si salen solos mientras pintan por GPU, el driver los hace fallar). Si el proceso web falla en marcha, deja `<config>/render-cpu`, vuelve a la CPU y reinicia (Conexiones → Gráficos tiene «Volver a probar la GPU»). Ojo al probar: matar el proceso web desde fuera cuenta como fallo y deja esa marca. Si `WEBKIT_DISABLE_DMABUF_RENDERER` o `WEBKIT_DMABUF_RENDERER_FORCE_SHM` vienen del entorno, no toca nada.
- `skills.rs`: skills del vault (`skills_list`, `skills_remove` a la papelera, `skills_prepare`), su frontmatter (entiende comillas y bloques `|`/`>`), la huella que usa el vigilante y `install_agent`, que deja `creador-de-skills` en `.claude/agents/`; `claude_code_start` lo instala antes de arrancar Claude Code (lee los agentes al empezar la sesión) y el prompt del orquestador le manda delegar en él toda skill nueva.
- `agents.rs`: agentes de `.claude/agents/` (también en subcarpetas; sin `description` no cuentan): `agents_list` (nombre, resumen, `model`, `effort`, `tools`, si lo mantiene nexo) y `agents_remove` a la papelera, más su huella para el vigilante.
- `registro.rs`: registro de agentes de la vista Agentes. `agent_log` lee las transcripciones de Claude Code (`~/.claude/projects/<carpeta del vault>/<sesión>.jsonl` = el orquestador; `<sesión>/subagents/agent-*.jsonl` + `.meta.json` = cada subagente, con su `agentType` y la tarea) y devuelve tokens, coste y modelo de cada agente con llamadas en la sesión de 5 h actual (ventana = `resets_at` − 5 h de `usage::claude_session`; sin sesión en curso, vacío). Si la sesión que dio Claude ya terminó o no hay datos, `resolve_window` la deduce de las llamadas de todo el equipo (cada sesión empieza con la primera llamada tras el final de la anterior, redondeada a 10 min; sin datos, tras el último hueco de 5 h) y no hay porcentaje. Un subagente termina al entregar su informe, al acabar con texto o cuando su sesión recibe el `<task-notification>` con su id (también si falló o lo detuvieron). Cada respuesta ocupa varias líneas con el mismo `message.id`: se cuenta una vez (y una sola vez entre archivos, por si una sesión se bifurcó). Los subagentes guardan el `output_tokens` del inicio del streaming: se estima con lo que escribieron (`CHARS_PER_TOKEN`). Los precios son los del catálogo de modelos de Claude Code (`price`; la prueba comprueba que da el mismo `costUSD`). El % de la sesión de 5 h de cada agente = su coste × (% que dio Claude ÷ coste de **todo** Claude Code del equipo hasta ese momento) (el endpoint solo da el total de la cuenta); con esa misma proporción el % usado se pone al día entre lecturas (`assign_shares`). Las transcripciones se leen incrementalmente (desplazamiento por archivo en `RegistroState`). `agent_context` es el `/context` de un agente: lanza `claude -p --input-format stream-json --no-session-persistence --strict-mcp-config` (hooks desactivados) y le manda la petición de control `get_context_usage` (`detail: summary`, no llama al modelo); para el orquestador con `--resume <sesión> --fork-session` (y el prompt del orquestador), para un subagente con `--agent <tipo>`, y el total sale de su última llamada.
- `connections.rs`: estado de MarkItDown (saludo MCP + `tools/list`), API (Models API, sin tokens), Antigravity y Claude Code.

El streaming hacia la interfaz usa `tauri::ipc::Channel` (eventos `{kind, text}`); la única excepción es `agy-activity`, un evento global porque el panel de actividad escucha todas las tareas de Antigravity.

**Frontend (`src/`)**:

- `main.js`: estado y cableado de toda la UI (vault, fuentes y su pestaña de resumen, conexiones, terminal/comandos, pestañas, actividad de Antigravity, vistas y escenas). `sendToClaude(texto)` abre la terminal de Claude Code (y la sesión si hace falta) y le escribe un mensaje: lo usan «Agregar skill» (pide al orquestador que use `creador-de-skills`) y «Usar en Claude Code» (`/<skill>`). Al añadir fuentes: ficha inmediata → conversión MarkItDown → resumen en la cola de Antigravity. En la pestaña API, los comandos conocidos (`COMMANDS`) se ejecutan y cualquier otro texto va al chat de Nexo.
- `graph.js`: grafo en canvas con d3-force/d3-zoom y paleta "galaxia" (neones suaves por tema, `colorFor`; cada nodo es una estrella, las fuentes en ámbar y los índices de fuentes, conversaciones y notas como minigalaxias espirales; sin fondo). Estrellas, halos y galaxias se pintan una vez en **sprites** (caché por color y tamaño en pantalla) y se copian; las aristas se trazan agrupadas por estilo. El pulso del nodo en foco y las ondas de los nodos nuevos van en una segunda capa (`.graph-fx`) que solo repinta su rectángulo: el grafo entero solo se redibuja cuando algo cambia. Las etiquetas se colocan por prioridad (foco, ratón, índices, fuentes, más conexiones) sin tapar otras etiquetas ni estrellas: prueban a la derecha, izquierda, encima y debajo, y si no caben no se dibujan (aparecen al pasar el ratón); su ancho se mide una vez (`labelWidth`). Al cargar, la vista sigue al grafo mientras la simulación lo coloca (`following`/`follow`) y deja de hacerlo cuando el usuario mueve o acerca, o al encuadrar a propósito. `setData` no reinicia la simulación si nodos y aristas son los mismos, y `setActive(false)` (vista Notas o cartas expandidas) deja de dibujar. `focus(id)` centra un nodo y `reveal()` lo hace crecer desde el centro al abrirlo desde la galaxia. **Nada de `transform` CSS en los lienzos del grafo**: `resize()` mide con `clientWidth`/`clientHeight`, pero el resto del código y d3 usan `getBoundingClientRect` (que incluye transformaciones); con el lienzo escalado el mapa de bits quedaba pequeño y el grafo se veía como una imagen estirada que no respondía al ratón. Las capas superiores usan `pointer-events: none` para que el ratón llegue al canvas salvo en paneles y controles; `getViewport()` calcula el hueco central entre paneles para centrar.
- `galaxy.js`: la galaxia inicial. ~16 000 puntos blancos (núcleo, disco tenue, aro con grumos y halo; `LOOK` y `makePoints`, deterministas) dibujados con **WebGL en un solo `drawArrays`**: la órbita de cada punto la calcula el shader con el tiempo, así que la CPU no hace nada por fotograma. Sin WebGL (pintado por CPU) usa un canvas 2D con un tercio de los puntos. `open()`/`close()` dispersan o recogen los puntos (`u_spread`), `contains()` es la zona clicable y `onFrame` avisa cuando cambian centro o tamaño (los toma del `#stage`; `main.js` lo usa también para centrar la luz de fondo, `--glow-x`/`--glow-y` de `.backdrop`). El tamaño sale de `frameFor` (ancho del hueco ÷ 2,85, con un tope en huecos estrechos para que las skills de los lados no pisen el anillo) y va a juego con `ORBIT` de `skills.js`: si cambia uno, revisar el otro.
- `skills.js`: recuadros de las skills en órbita alrededor de la galaxia (`ORBIT`, `orbitLayout` los reparte sin pisarse; con más de `ORBIT.max` aparece «+N»), el resumen al pulsar uno (`#skill-pop`, solo nombre, descripción y `/comando`) y la carta Agentes → Skills (lista, «Agregar skill» y filas «Creando skill…» hasta que el vigilante avisa de una skill nueva).
- `agents.js`: pestañas Skills / Agentes de la carta Agentes (`nexo.agentsTab`) y lista de agentes con el modelo y el esfuerzo legibles (`modelLabel`, `effortLabel`, `toolsLabel` agrupa las herramientas MCP por servidor); «Agregar agente» pide a Claude Code, con el modelo y el esfuerzo elegidos, que `creador-de-skills` lo escriba.
- `registro.js`: el registro de agentes en el centro de la vista Agentes (`#agent-log`): resumen de la sesión de 5 h (agentes de nexo frente al resto de Claude), agentes activos y terminados con sus tokens y su parte de la sesión, y al abrir uno su contexto como `/context` (barra a escala de la ventana con un tramo por categoría, `contextSegments`, con un mínimo para que se vea lo diminuto; categorías traducidas en `CATEGORY`), su uso en la sesión, la conversación por tipo y listas plegables (adjuntos, herramientas, skills, agentes, memoria, MCP). Secciones planas separadas por líneas finas; el resumen de la sesión queda arriba también en el detalle. Solo consulta mientras se ve (`activate`, cada 5 s).
- `note-view.js`: Markdown de las notas → HTML con `marked` (extensión para `[[enlaces]]`) **siempre pasado por DOMPurify** (las notas pueden traer contenido de webs) y `resolveLink`, que resuelve enlaces igual que `graph.rs`. Al elegir un nodo que no es fuente, `main.js` (`showNode`) muestra en la carta de la izquierda su contenido (`note_view`: cuerpo sin frontmatter + propiedades), sus conexiones y enlaces que llevan a otros nodos.
- `note-editor.js`: editor por bloques al estilo de Notion que guarda Markdown. Cada línea es un bloque con su propio `contenteditable="plaintext-only"`; Intro, Retroceso, Supr, flechas, Tab y Ctrl+Z/Mayús+Z los maneja el editor (historial propio). El «+» de la línea vacía y «/» al empezar una línea abren el menú de bloques; también valen los atajos de Markdown (`- `, `[] `, `1. `, `# `, `> `, `---`, ```` ``` ````). La línea con el foco se ve como Markdown y las demás con formato (negrita, enlaces, `[[…]]`, fechas 📅 que avisan si vencen), con el cursor colocado en su sitio del Markdown al hacer clic. Lo que no se toca se serializa **byte a byte igual** (`raw`), y siempre hay una línea vacía final (`ghost`) que no se guarda si nadie escribe en ella. `parseMarkdown`/`serializeBlocks` no usan el DOM (se pueden probar con node).
- `notes.js`: vista Notas. Carta izquierda con temas/subtemas (navegación con migas) y notas; escritorio central con cartas que se mueven (cabecera, con `transform` mientras se arrastra), redimensionan (esquina), cambian de capa, se renombran (doble clic en la cabecera), muestran su Markdown (`</>`) y se ordenan en rejilla sin encimarse; las nuevas buscan un hueco libre visible. Las cartas nunca se recolocan ni encogen solas: si el escritorio se estrecha, se desplaza (su barra lo indica; un borde iluminado se probó y parecía un fallo de pintado). Cada carta lleva un `note-editor`; sus guardados van en fila (nunca dos `note_save` a la vez). Reacciona a `wiki-changed` (recarga las cartas que no se están usando; las que sí, al salir de ellas) y a `desk-changed` (Claude Code cambió `.nexo/escritorio.json`).
- `dom.js`: `reconcile(lista, elementos, {key, sig, build})` deja una lista del DOM al día reutilizando las filas que no cambiaron; solo las nuevas llevan `enter` (su animación de entrada). Úsalo para listas que se recargan a menudo (fuentes, notas, actividad): reconstruirlas con `replaceChildren` repetía la animación y la carta parpadeaba.
- `claude-code.js`: xterm.js conectado a los comandos `claude_code_*`. Las pulsaciones se envían en orden y agrupadas (cola `send`); `show()` reajusta, repinta y enfoca al volver a mostrarse (xterm deja de dibujar mientras está oculto). `say(text)` escribe y envía un mensaje (lo usa "Guardar en el grafo").
- Solo `main.js` distingue escritorio/navegador con `isTauri()`; en el navegador las funciones de Tauri muestran un aviso.

## Cosas que no se ven a simple vista

- **Altura fija**: `.app` mide exactamente `100dvh` y cada carta hace scroll por dentro. La cadena de contenedores flex necesita `min-height: 0` hasta la lista o terminal que se desplaza; si se quita en algún nivel, la app vuelve a crecer con el contenido. En la carta de fuentes solo encogen la lista, el resumen y el estado vacío (lo demás lleva `flex-shrink: 0`; antes, a 720 px de alto, los filtros se aplastaban); con una fuente abierta en ventanas de ≤ 820 px de alto se apartan «Añadir fuente», el enlace y «Leer con».
- **Ventanas estrechas**: con ≤ 1440 px de ancho la barra del grafo se compacta en una fila (sin separadores, «Profundidad» solo como número) y con ≤ 1240 px «Etiquetas» queda solo para lectores de pantalla. Va con `@media` y no con `@container` en `.stage`, que afectaría a lo que lleva dentro.
- **Cartas laterales acopladas**: `.panel` es una sola superficie recta acoplada al borde de la ventana, a `--edge` (14 px) de él para que su línea de ese lado se vea entera junto al marco de la ventana (pegada en el píxel 0 quedaba tapada), con una línea fina (`--seam`) en sus cuatro lados y 20 px arriba y abajo; no hay tarjetas dentro de la carta: las secciones se separan con costuras a sangre (bajo «Leer con», el pie «En contexto», bajo las herramientas de la terminal). Los anchos son `--left-w`/`--right-w` (`clamp` con la ventana; con 424 px la cabecera de la terminal cabe con «Claude Code»). Lo que ganan las cartas sale de los márgenes que tenían, así que el hueco de la galaxia casi no cambia; si se ensanchan más, la galaxia encoge (ver `frameFor`). Con una carta expandida los lienzos se ocultan para que no asomen por la rendija. Las casillas son propias (`.source-check`, `.ne-check`, con la palomita `--check-mark`): la nativa de WebKitGTK sale descentrada.
- **Contraste**: `--faint` (0.5) es el gris más claro para texto (≈ 5:1 sobre las cartas) y no hay texto por debajo de 11 px.
- **Rendimiento en WebKitGTK**: evitar `backdrop-filter` (con el grafo animado detrás, cada fotograma obliga a redesenfocar) y sombras con difuminado grande en lo que se mueve; las animaciones que corren siempre deben repintar solo un rectángulo pequeño (como `.graph-fx`). Con el pintado por GPU de nexo, WebKit copia por memoria compartida cada fotograma de lo que cambia: por eso el lienzo de la galaxia en reposo solo cubre su rectángulo (`galaxyExtent`, toda la ventana solo mientras se dispersa) y se repinta como mucho a 60 fps (`IDLE_FPS`; transiciones y ratón a la frecuencia del monitor). Medido a 120 Hz: ~35 % de un núcleo → ~19 % entre WebKit, la ventana y Hyprland. Para medir, `MiniBrowser` (`/usr/lib/webkit2gtk-4.1/`) con las mismas variables que pone `render.rs` es el mismo motor que la app.
- **Clases genéricas**: `.empty`, `.chip`, `.toolbar`… ya tienen estilos globales; las clases de un componente llevan su prefijo (`ne-` en el editor) para no heredarlos (un `.empty` dentro del editor centraba el cursor).
- **Cartas expandibles**: las clases `expand-left`/`expand-right`/`expanded` de `.layout` pliegan el `.stage` (flex 0, margen negativo que absorbe un hueco) y hacen crecer la carta hasta el borde de la otra; con las dos, ambas pasan a `flex: 999 1 0` y se reparten el ancho. Solo en ≥768px; el estado vive en `localStorage` (`nexo.expanded`). WebKitGTK deja rastros de 1 px del borde de la carta en la franja que esta deja libre durante la transición de ancho (al minimizar se veían líneas verticales): al acabar cada transición `main.js` cambia el fondo casi transparente de `.layout` para repintarla entera.
- **Vistas y escenas**: `setView` (`grafo`/`notas`/`agentes`, en `localStorage` `nexo.view`) cambia el núcleo de la carta izquierda (`.panel-core.sources` ↔ `#notes-core` ↔ `#agents-core`). Lo que se ve en el centro es la escena (`body[data-scene]`: `galaxia`, `grafo`, `escritorio` o `registro`): en Grafo depende del plano que eligió el usuario (`nexo.plano`; la galaxia por defecto, «Abrir grafo» o un clic en la galaxia lo cambian y se recuerda), Agentes muestra el registro de agentes (`#agent-log`) y Notas el escritorio (`#desk`). El CSS de las escenas oculta/muestra lienzos, barra y recuadros; `syncGraphActive` deja de dibujar lo que no se ve. Navegar a un nodo (búsqueda, «Ver en el grafo», enlaces) usa `showInGraph`, que abre el grafo; los enfoques implícitos (abrir una fuente) no cambian de plano. La terminal se minimiza a un riel (`.layout.min-right`, `nexo.minimized`); al restaurarla se llama a `claudeCode.show()` porque xterm no dibuja oculto. Al expandir/contraer la carta derecha o restaurarla, el teclado va al chat (`focusChat`). xterm solo se reajusta cuando el panel deja de cambiar de tamaño (`scheduleFit`): cada reajuste redimensiona el PTY y Claude Code redibuja toda su pantalla.
- **El vigilante de `wiki/`** (`graph::watch`, cada segundo) emite `wiki-changed` con `added` y `changed`, llama a `notas::sync` si cambió algo en `notas/`, emite `desk-changed` si `.nexo/escritorio.json` cambió fuera de nexo, `skills-changed` (con las skills nuevas) si cambió `.claude/skills/` y `agents-changed` si cambió `.claude/agents/`.
- **Recarga de Vite ≠ reinicio**: al guardar un `.js`, Vite recarga la ventana y se pierde el estado del frontend, pero el backend sigue vivo (sesión PTY de Claude Code, trabajos de agy). Por eso el lector del PTY sigue vaciando la salida aunque el `Channel` ya no tenga destinatario; si se detuviera, el PTY se llenaría y bloquearía a Claude Code. Cambiar código en `src-tauri/` sí reinicia la app.
- **La sesión de Claude Code depende de la carpeta**: Claude Code guarda sesiones y memoria por `cwd` (`~/.claude/projects/<cwd codificado>/`). Las sesiones de nexo arrancan en la raíz del vault; si se cambia esa carpeta, `--resume` no encuentra la sesión y la memoria del orquestador queda en otro sitio.

## Impeccable: crítica, auditoría y pulido

`.claude/skills/impeccable` viene de `pbakaus/impeccable` (instalada con `npx skills add`, versión fijada en `skills-lock.json`). Se usa cuando se pide: `critique`, `audit` o `polish` (sus guías están en `reference/`) y, a diferencia de las de abajo, sus recomendaciones sí se aplican si el usuario lo pide. Su lanzador (`scripts/impeccable`) descarga una vez su motor verificado a `~/.impeccable/bin/`; `impeccable detect --json index.html src` es el detector de patrones y las críticas se archivan en `.impeccable/critique/`. El aviso `side-tab` por el `border-left` de las citas de las notas es un falso positivo. Las decisiones de este archivo mandan sobre sus reglas genéricas, como con las de abajo (la etiqueta sobre el título de cada carta, «Cuaderno», la pidió el usuario aunque Impeccable prohíbe los *eyebrows*).

## Skills de diseño: solo diagnóstico

`.claude/skills/design-taste-frontend` y `.claude/skills/redesign-existing-projects` vienen de `Leonxlnx/taste-skill` (instaladas con `npx skills add`, versión fijada en `skills-lock.json`). **Solo sirven para dar diagnósticos de diseño**: cuando se pida revisar o diagnosticar el diseño, se usan como lista de comprobación y la respuesta es un diagnóstico (qué falla, dónde, con `archivo:línea`, por qué y qué se propone), ordenado por impacto.

- Mientras se diagnostica no se edita ningún archivo, no se instalan paquetes ni fuentes y no se generan imágenes, aunque la skill lo pida (sus pasos «Fix», «Upgrade», el uso obligatorio de generadores de imágenes y el «Pre-Flight Check» de código no aplican). Los cambios se hacen solo si el usuario los pide después, como cualquier otra tarea.
- Están pensadas para webs y landings; nexo es una app de escritorio densa (`design-taste-frontend` excluye expresamente los paneles de producto). Se aplica solo lo que tenga sentido aquí y se dice cuándo una regla no encaja.
- Las decisiones de este archivo mandan sobre sus recomendaciones genéricas: nada de `backdrop-filter`, ruido o sombras grandes en lo que se mueve (rendimiento en WebKitGTK), la tipografía y el estilo «Órbita» elegidos por el usuario, la escala real de la barra de contexto, etc. Si una de ellas choca con la skill, se menciona como observación, no como fallo.
